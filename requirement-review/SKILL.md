# 需求体检（Requirement Review）

本质是**帮用户把需求理清楚**，而不是急着实现。检查三件事：

1. **与现有内容的关系**：冲突、契合（已有可复用），还是影响到了什么？
2. **需求是否充分**：补出边界情况与不常见用法，给出补充建议。
3. **AI 是否真正理解**：不确定就先问清，清楚后输出「理解说明」供确认。

不一定每次全跑，按复杂度分两档，开头声明「本次按第 X 档处理」。全程中文。

## 何时触发

- **仅手动触发**（`disable-model-invocation: true`）：用户点名本技能，或说「需求体检 / 预检 / 帮我看下这个需求 / review requirement」。
- 需求来源：对话文字，或指向的文档/文件。

## 核心理念

- 目的：理清需求，不出方案、不实现。
- 先疑虑、后结论：「理解说明」放最后（理解错了，后面分析都白搭）。
- 可伸缩：按「影响面 + 不确定性」判档，简单需求别过度分析。

## 两档自适应

### 第 1 档 · 简单需求（如小改 UI）

- 只输出「理解说明」。
- 若明显撞见与现有内容冲突，一句话提醒即可，不展开。
- 信号：改动小、影响面窄、基本无歧义。

### 第 2 档 · 需求分析 / 业务逻辑梳理

A → B → C：

- **A 初步认识 + 疑问清单**：先做**轻量定向冲突扫描**（方法见 ①，只看明显相关点）来形成问题；给一段初步认识，再把不清楚的点、边界处理、补充点做成**带选项的问题**抛出，等用户回答。
- **B 追问到无疑问**：按回答更新认识，有疑问继续问，直到没有疑问。
- **C 冲突分析 + 最终理解说明**：无疑问后做正式冲突分析（见 ①），输出分析 + 最终理解说明供确认。
- 信号：要梳理业务逻辑、跨模块、改接口、有明显歧义。

> 两档由 AI 判断，用户可要求加档/降档。

## ① 与现有内容的关系

主动查并报告（用户未必知道是否冲突或已有类似实现）。

- **范围**：当前仓库代码 + 仓库内文档（README / AGENTS.md / 待办 / ADR / issue 等）+ 用户给的上下文。
- **方法**：按**功能相关方向定向搜索**（领域概念而非字面措辞），读相关模块与文档；**不做全仓扫描**，除非用户要求「深挖」。
- **报四类关系**（按优先级）：**冲突**（矛盾/重复实现）→ **影响**（波及的模块/接口/文档）→ **契合**（已有可复用）→ **无关联**（未发现，可请用户补充线索）。
- 每条尽量给证据定位（`文件:行号` / 文档段）。
- 非代码仓库：跳过代码排查，仅凭上下文判断说明。

## ② 边界情况与补充

用户常只想到正常路径，这里补不常见 / 遗漏的点。

- 不用固定清单，用**更高层思考角度**、相关才展开：
  - **场景**：谁、什么环境/时机、别的角色/用法/前后置条件？
  - **输入**：空、极端、异常、组合输入各会怎样？
  - **状态与流程**：重复操作、并发、失败重试、顺序调换、中途取消/回退？
- 不硬凑，不适用的角度跳过；每条附一句「为什么要考虑」。
- 需要用户拍板的，在步骤 A 做成带选项的问题先问；纯提示类放最终分析。

## ③ 理解核对

最终输出「理解说明」供确认，按需覆盖：目标/要解决的问题、**要做什么**（「不做什么」可选）、关键行为与规则、输入/输出（若有）、约束与前提（**显式列假设**）、怎样算完成/验收（若能判断）。篇幅随复杂度自适应。仍有没把握的点就先回去问，无疑问再输出。

## 定级与提问

- 最终分析里把「确认要做」的补充项按 `必须 / 建议 / 可选` 简述，各附一句为什么；已解决 / 不需要的不重复。
- 提问：优先选择题（选项 + 一句背景 + 「其他/自定义」）；一次问一批相关问题，等答完再继续；每题说清「为什么问」。

## 交付

默认只在对话输出；用户明确要求时才落 Markdown 文件。

## 边界与安全

- 需求简单或与现有无关 → 走第 1 档，别过度分析。
- 找不到相关代码/文档 → 如实说「未发现」，不臆造依据。
- 多个需求混在一起 → 先拆开逐个处理。
- 只读为主；除用户要求，不修改文件、不执行有副作用操作。

## 收尾

输出后询问：理解是否一致 / 还需补充什么，按反馈修正。
