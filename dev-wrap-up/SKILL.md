# 开发收尾（Dev Wrap-Up）

一次开发结束后，按固定顺序完成三件事：**复盘 → 文档同步 → 提交**。

- 读操作（复盘、检查文档）可以直接进行。
- 写操作（修改文档、`git commit`）在「需要确认」的场景下，要先把改动/草案拿给用户看，经确认后再落地。
- 全程以中文工作。

## 何时触发

- **显式触发**：用户说「收尾 / 复盘 / wrap up / 开发完成 / 收个尾」等，进入完整流程。
- **主动触发**：AI 察觉一次开发任务已完成（代码改完并做过基本验证）时，**不要擅自开跑**，先问用户要不要收尾、要做哪些环节，**由用户选择**。用户确认前不执行任何写操作。
- **被其他技能引用**：其他 Skill 可以直接按名字 `dev-wrap-up` 提到本技能来唤起它。

## 总览

```
环节一 · 复盘  →  环节二 · 文档同步  →  环节三 · 提交
```

三环节顺序固定；但「是否一路做到提交」取决于下面的判断规则——有时需要先停下等用户反馈。

---

## 环节一 · 复盘

把这次开发讲清楚，**只输出到对话里，不生成文件**。默认**不跑测试**（开发阶段通常已测过），除非用户明确要求。

按以下 6 节输出：

1. **需求/问题背景**：这次要解决什么——用户要什么功能、修什么 bug、达成什么目标。
2. **实现思路与方法**：是怎么做的。可详述：关键设计、算法、数据结构、方案取舍、踩过的坑与如何解决。
3. **涉及模块与文件**：列出改动/新增的模块、文件、接口、关键函数。
4. **验证情况**：记录开发阶段已做或未做的测试、构建结果；没有就如实写「开发阶段未做/未提供」。
5. **风险与遗留**：未完成项、已知问题、兼容性/性能等注意事项。
6. **后续建议**（可选）：值得继续做的事。

复盘时若**发现问题**（bug、未完成、不确定的设计等），务必写清楚——它会影响下一步是否能直接提交。

---

## 环节二 · 文档同步

检查文档与实际实现是否一致，不一致就修正。

### 文档来源优先级

1. 优先看 `AGENTS.md` 等说明文件里**声明过的相关文档**（需求文档、架构文档、待办清单等）。
2. 若没有声明，AI 按**文件名与本改动的相关性**自行判断哪些文档重要、可能受影响。
3. 都判断不出时，按常识处理，并在报告中说明「未发现相关文档」。

### 简单 vs 复杂

- **简单（可直接修改）**
  - 完成状态变更：待办项「未完成 → 完成」、删掉已完成项。
  - 修正过期链接、路径、错别字。
  - 与实现明显不符的过时描述做微调。
  - 开发过程中已经去掉的点，从文档里相应移除。
- **复杂（交给用户决策）**
  - 架构/设计方向变更。
  - 需求范围的增删。
  - 接口 / 数据模型的变更。
  - 需要跨多份文档联动修改。
  - 含义不清、需要业务判断。

**简单**改动直接执行；**复杂**改动先列出「不一致清单 + 建议改法」，交用户决定，不要擅自动大改。

### 结束必须汇报

无论改没改，环节结束时都要说明：**改了哪些文档、各改了什么；若没有改动，也要说明「文档无需更新」或「未发现相关文档」**。

---

## 环节三 · 提交

### 3.1 是否直接提交（判断速查）

**默认优先直接提交**。满足以下**全部条件**时，直接提交、不打扰用户：

- 复盘**未发现任何问题**（无 bug、无未完成、无不确定设计）；
- 文档改动**全部属于简单/低风险**；
- 本次改动**范围小**（单文件或少文件，无破坏性）。

**只要出现任一条，就停下，不提交**，改为只做「复盘 + 文档改动预览」，把 **复盘内容 + 文档拟改 + 提交信息草案** 一起给用户，等确认后再提交：

- 复盘发现任何问题 / 风险 / 遗留；
- 文档改动属于复杂/重大；
- 用户事先说过「先不要提交」。

> 用户说「先别提交」时：只做前两个环节，然后把复盘内容与文档改动都说明清楚，等待用户反馈。
> 以上判断需要在每次执行时自行斟酌，而不是机械套用。

### 3.2 暂存范围

- 默认**根据本次开发实际改动的文件选择性 add**，不要无脑 `git add -A`。
- 若发现工作区里有**开发前就存在的、与本任务无关的未提交改动**，先停下来询问是否纳入，避免误提交。

### 3.3 提交信息格式（中文）

首行直截了当地说明本次提交做了什么；空一行后分「为什么 / 怎么做」；最后按需补充。模板：

```
<type(scope): 一句话直接说明本次提交做了什么>

【需求/背景】
为什么做：解决什么问题，来自哪个需求或 bug。

【实现方式】
怎么做的：关键方案、涉及模块与文件、重要改动点。

【补充】（可选，AI 视情况补充：风险、影响面、验证情况、关联 issue 等）

🤖 Generated with OpenCode
Refs: #123
```

规则：

- **首行**：用 Conventional Commits 前缀 `type(scope): 简述`（scope 可选，如 `feat(auth): 支持手机号登录`、`fix: 修复导出乱码`）。整行（含前缀）≤72 字符，不加句号，尽量直述。
- **正文**：`【需求/背景】` 讲清「为什么做」；`【实现方式】` 讲清「怎么做的、涉及哪些模块」，可详细。
- **补充**：可选，由 AI 根据实际情况决定写什么。
- **AI 署名**：默认加一行 `🤖 Generated with OpenCode`。
- **任务号**：能从分支名/上下文识别到任务或 Bug 号时，加一行 `Refs: #xxx`；识别不到就省略。
- 以上「首行 + 需求/背景 + 实现方式」是必须的，其余按实际情况增减。

### 3.4 提交前校验

默认**不跑测试 / lint / 构建**（与复盘一致，保持速度）。仅当用户明确要求时才执行，并把结果附在汇报里。

### 3.5 推送

默认**只 commit，不 push**。只有用户明确要求时才 push。

---

## 边界与安全

遇到以下情况，**先停下说明**，不要硬来：

- 当前目录不是 git 仓库 → 跳过提交环节并说明。
- 没有任何改动（空提交）→ 跳过并说明。
- 处于 detached HEAD 或异常分支 → 说明情况，询问如何处理。
- 待提交内容里有 `.env`、密钥、凭证等敏感文件 → 停下询问是否排除。
